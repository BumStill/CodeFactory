# Versioning policy

CodeFactory follows [SemVer](https://semver.org/) within the pre-1.0
constraint: while we're below 1.0.0, the minor version is the de-facto
"major" — bumping it signals a noticeable change to behaviour or shape
that a returning user should be aware of.

## When to bump which slot

| Slot | Bump when | Examples |
|---|---|---|
| **PATCH** `0.x.y → 0.x.y+1` | Bug fix, doc-only change, internal refactor, dependency update with no user-visible effect. | Tighten a thresh­old. Fix a misrender. Trim a feature flag. |
| **MINOR** `0.x.0 → 0.x+1.0` | New user-visible capability, behaviour change a user would notice, UX rework, removed/renamed surface that isn't strictly breaking but the user should know. | Auto-update. Git checkpoints. Project memory. Plan-first prompt. Settings panel rework. |
| **MAJOR** `0.x.0 → 1.0.0` | Product is stable enough that we'd recommend it to a new outside developer with a straight face. Reaching here is a deliberate call, not a slow drift. | The first time the answer to "should I install this?" is unconditionally yes. |

## When in doubt

Use minor. A 0.x family that quietly turns into a different product
through 30 patch bumps is harder to communicate than a clean
`0.4 → 0.5 → 0.6` arc with explicit deltas at each step.

## History rewind

For the record (in case anyone wonders why we jumped from 0.3.20 to 0.4.0):

- **0.3.0 – 0.3.3**: scaffolding + CI build-time optimisation (correctly
  patch-sized).
- **0.3.4 – 0.3.20**: should have been 4–5 minor releases. Auto-update,
  signed-installer pipeline, file-lock concurrency, context-window
  management, reasoning-content replay, project memory, plan-first prompt,
  TDD discipline, git checkpoints, scroll behaviour — all landed as
  patches because we didn't have a policy. This document is that policy.

From **0.4.0** onward, every release tag carries a short rationale in the
changelog explaining which slot was bumped and why, generated by
`cliff.toml` from conventional-commit prefixes:

- `fix:` → PATCH
- `feat:` → typically MINOR (the cliff template doesn't auto-decide,
  the release-cutter does — see below)
- `feat!:` or `BREAKING CHANGE:` footer → MAJOR

## Cutting a release

Do not manually commit a version bump, create a tag, or push `main` from a
developer checkout. The canonical path is the governed
[`auto-release.yml`](.github/workflows/auto-release.yml) workflow:

1. Run it from GitHub Actions with `workflow_dispatch` (or let the daily
   schedule batch the next eligible `feat`/`fix` changes). An already-authorized
   `deliver_changes -> through_release` request is the other supported on-demand
   entry point.
2. The workflow calculates the slot from all commits since the last tag, updates
   the version manifests on `automation/release-next`, and opens a normal PR.
3. That PR runs the same required checks, including the README contract, before
   a guarded squash merge. Its body declares `README-Update: reviewed` because
   version-only changes do not alter the evergreen README contract.
4. After the guarded merge, the workflow creates the tag and dispatches
   [`release.yml`](.github/workflows/release.yml), which builds the Windows and
   macOS assets and publishes Release notes.

The legacy `scripts/bump-version.ps1` helper is not a release entry point. It may
be used only as an explicitly reviewed local manifest helper; it must not push
`main` or tags. Release-specific versions and details stay in GitHub Release
notes, not in `README.md`.
