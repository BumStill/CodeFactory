## git 元数据写入面（本轮补强的阻断修复）

真实工作区往往是 linked worktree：`.git` 是一个文件，指向 `<common>/worktrees/<id>`，
index、objects、refs、logs 都在工作区之外。沙箱一旦生效而不放行这些路径，会话里的
`git add` / `commit` / `merge` 会全部失败（R10 早期版本用临时普通仓库，属于假绿）。

现在的做法（`trusted_sandbox::git_paths`，路径由 `git rev-parse --git-dir --git-common-dir`
取得并规范化）：

- linked worktree：整棵放行本工作区的元数据目录 `worktrees/<id>`；common dir 只放行
  `objects`、`refs`、`logs`、`worktrees`、`branches`、`modules`，以及 `packed-refs`、
  `packed-refs.lock`、`FETCH_HEAD`、`ORIG_HEAD`、`MERGE_HEAD`、`CHERRY_PICK_HEAD`、
  `REVERT_HEAD`、`shallow`、`gc.log` 这些单文件（叶子允许尚不存在，仍只放行该名字）。
- 普通仓库（git dir 就是 common dir）：index/HEAD/index.lock 在 common 根上，必须整棵放行，
  再由后置 `deny` 把 `config`、`config.worktree` 与 `hooks/` 锁死（后置规则覆盖前序 allow）。

拒写证据：`src-tauri/src/agent/trusted_sandbox.rs::tests::git_config_hooks_and_main_checkout_stay_read_only`
（linked worktree）与 `src-tauri/src/agent/trusted_sandbox.rs::tests::git_operations_work_in_a_plain_repository_without_opening_config`
（普通仓库）；矩阵另有三条同名拒写用例。

**git 流程是否需要写 config？** 不需要。矩阵里 commit、merge、worktree add 都只写
objects/refs/logs/index/HEAD，`config` 与 `hooks/` 全程只读即通过。于是 `git config` 在沙箱内
会失败——这是有意的（写 config 等于允许沙箱内进程把 `core.hooksPath`、`core.fsmonitor`
或别名指向沙箱外可执行文件）。已知边界：sandbox 内不能跑需要写 `packed-refs`（`git gc` /
`git pack-refs`）或写 common 根上其他新文件的操作；`packed-refs` 已按单文件放行，首次由
gc 创建时会失败，遇到再单独处理。

## ~/.cargo 与 ~/.rustup 收窄

初版把整个 `~/.cargo` 放行，等于允许沙箱内进程往 `~/.cargo/bin` 写可执行文件、或改
`~/.cargo/config.toml` 让下次构建加载外部命令。现在只放行 `registry`、`git` 两个子树与包缓存锁
文件 `~/.cargo/.package-cache`；`bin/` 与 `config.toml` 不在白名单。`~/.rustup` 完全不放行——
构建只读 toolchain，可写等于允许替换编译器。证据
`src-tauri/src/agent/trusted_sandbox.rs::tests::cargo_payload_paths_stay_read_only`（profile 断言 +
真实写入 `~/.cargo/bin/m224-probe` 被拒），矩阵 cargo-test 在同样收窄的策略内仍通过。

## 信号边界

`(allow signal)` 过宽：沙箱内进程能给同一用户下任意进程发信号（实测 `(target pgrp self)`
甚至能杀掉沙箱外进程）。现为 `(allow signal (target same-sandbox))`：

- `src-tauri/src/agent/trusted_sandbox.rs::tests::signals_cannot_escape_the_sandbox`：沙箱内 kill 沙箱外进程失败且目标存活。
- `src-tauri/src/agent/trusted_sandbox.rs::tests::signals_reach_processes_inside_the_same_sandbox`：沙箱内结束自己的子进程成功（vitest/cargo 不会挂死）。

## 沙箱内全量 cargo test 的处理办法

macOS 不允许嵌套沙箱（沙箱内再调 `sandbox-exec` 会得到 `sandbox_apply: Operation not permitted`），
所以分层执行，两层都要绿：

1. **宿主侧**跑沙箱自身套件：`cargo test --lib -- trusted_sandbox`（16/16，真实 Seatbelt）。
2. **沙箱内**跑项目测试与真实工作流：矩阵 cargo-test 执行 `cargo test --lib -- config::settings`，
   外加 pnpm vitest / build、real-linked-worktree 的 git 流程、后台任务与浏览器。
   筛掉 `trusted_sandbox` 不是跳过验收，而是那批用例本身要在宿主侧建沙箱。

矩阵与账本都写明这条限制，报告 JSON 保留每项真实耗时与输出尾部。
