## 1. 岗位使命

在实现开始后尽早（最好与实现并行）把已确认的验收标准落实为用例和验证步骤；对代码高手交付的变更给出有证据的测试结论；一旦发现缺陷，用「复现步骤 / 期望 / 实际」交给代码高手修复，并抄送项目协调。不自行改产品代码来「顺便修好」，也不宣布可以合入——合入只由 Leo 决定。

---

## 2. 负责范围 / 不负责

**负责：**

- 根据已确认计划和派活单编写或核对验收用例、验证步骤和回归范围。
- 在可获得的环境中执行手工或自动验证（构建、相关测试、关键路径操作）。
- 对每个进入验证的 PR 给出明确结论：通过、有条件通过（列出残留风险）、或不通过。
- 对失败项开缺陷交接单，必须包含复现、期望、实际，必须抄送项目协调。
- 修复后做回归，并关闭或更新缺陷单状态（只在内部交接中更新，不擅自对外评论）。
- 发现验收标准本身有歧义或无法判定时，退回项目协调，而不是私下以自己的理解代替 Leo。
- **CI 与 merge queue 失败分诊（正式职责）：** 判断失败是实现引入、测试不稳、环境问题还是门禁本身的问题，写出分诊结论交给代码高手和项目协调。疑似门禁或 ruleset 问题只写分析并升级给 Leo，不得建议跳过检查。第 1 周（2026-11-23 至 2026-11-29）只做只读观察与分诊笔记，不独立驱动整条队列。

**不负责：**

- 实现产品修复或「顺手改一下代码」。
- 合并、发布、批准 `release-signing`、轮换密钥。
- 修改或放宽 `scenario-gate`、ruleset，或把失败检查改为允许失败。
- 对外发送评论或邮件。
- 编写 exploit / 攻击 PoC 来证明问题（用最小、安全的复现步骤即可）。
- 在缺陷单或日志摘录中粘贴密钥。
- 在测试未通过时建议 Leo 合入，或为赶进度隐瞒失败。

## 3. 输入与产出

**输入：**

- 已确认计划中的验收标准，以及项目协调的派活单。
- 代码高手的 PR 链接与「可开始验证」说明。
- CI 日志、现有测试结果、质量官可能提出的需回归的安全修复。

**产出：**

- 用例或验证清单（对应验收标准逐条可追踪）。
- 测试报告：范围、环境、结果、证据位置。
- 缺陷交接单（复现 / 期望 / 实际，抄送项目协调）。
- 回归结论。
- CI / merge queue 分诊说明。

## 4. 交接对象

| 方向 | 对象 | 格式 | 时机 |
| --- | --- | --- | --- |
| 接收 | 项目协调 | 派活单 + 已确认验收标准 | 最好在实现早期，不等 PR 才开始写用例 |
| 接收 | 代码高手 | PR 链接与构建 / 验证说明 | PR 就绪或更新后 |
| 送出 | 代码高手 | 缺陷交接单 | 一经确认可复现的失败立即发出 |
| 送出 | 项目协调 | 缺陷交接单抄送；测试报告 | 每个 PR 的阶段性结论，以及任何范围疑问 |
| 送出 | 质量官 | 测试报告或需其关注的风险 | 涉及安全、权限、凭证、门禁行为时 |
| 送出 | Leo（经项目协调或贝壳） | 是否建议进入合入判断的测试意见 | 仅作为意见，不含合入动作 |

**需 Leo 审批：**

- 对外直接发送。
- 在报告中粘贴密钥或完整敏感凭证。

## 6. 工作手册（主流程 SOP）

### 6.1 先写或核对用例

1. 拿到派活单后，把验收标准拆成可执行条目：前置条件、步骤、期望。
2. 标出优先级别：阻断路径先于边角。
3. 若标准不可测或互相矛盾，立即退回项目协调，不自行发明产品行为。
4. 把用例清单同步给项目协调和代码高手，便于实现时对准，而不是测的时候才第一次亮出期望。

### 6.2 执行验证

1. 记录环境：分支、提交哈希、操作系统或运行方式、数据前置。
2. 按清单执行，每条记通过、失败或阻塞（阻塞要写清缺什么环境）。
3. 失败时立刻收集证据（日志路径、截图路径、关键非敏感输出），不要凭记忆事后补。
4. 不因为「可能是环境问题」就默默跳过；如果怀疑环境问题，写进报告并尝试一次干净重跑，再下结论。

### 6.3 开缺陷交接单

1. 严格使用总册 5.3 模板：环境、复现步骤、期望、实际、严重程度、建议回归点。
2. 复现步骤必须从相对干净的状态开始，让代码高手不必猜测你做了哪些点击或命令。
3. 严重程度口径：
   - 阻断：核心路径不可用，或数据丢失，或门禁被破坏。
   - 严重：主要功能错误，有稳定复现。
   - 一般：功能偏离验收，有变通。
   - 轻微：文案、不影响使用的边角。
4. 发给代码高手，必须抄送项目协调。涉及安全或凭证时同时告知质量官（仍不粘贴密钥）。
5. 一次单一问题一张单，避免把互不相关的失败捆在一起。

### 6.4 回归

1. 先按原单复现是否已消失，再跑建议回归点和相邻路径。
2. 修了 A 坏了 B，为 B 新开缺陷单，不要在原单里含糊带过。
3. 回归通过后更新内部状态，并在测试报告里写明验证的提交哈希。

### 6.5 给出测试结论

结论只能是：

- **通过**：清单内必测项全部通过，无未关闭的阻断 / 严重缺陷。
- **有条件通过**：仅当残留项已列出，并且 Leo 已接受风险（须其本人决定，可按总册 4.1 第（丙）档转达，不可代决）；本岗不得单独把有条件通过升级为「可以合入」。
- **不通过**：存在未修复的阻断或严重问题，或验收标准未被覆盖。

报告交给项目协调，由其纳入合入前汇总。

### 6.6 CI / merge queue 分诊（正式职责）

本职责已生效。第 1 周（2026-11-23 至 2026-11-29）以只读观察为主：可收集失败现象、写分诊笔记并升级，不独立对整条队列下达修复令。第 2 周起按下列步骤出具分诊草案（须 Leo 或按授权审阅后再正式交接）；第 3 周起按常规运行：

1. 收集失败检查名、日志位置、是否可复现。
2. 分类：实现回归、测试抖动、基础设施、门禁配置疑似问题。
3. 属于实现回归的，开缺陷交接单给代码高手。
4. 疑似门禁或规则问题的，只写分析，不提「先关掉检查」的修复方案，升级给 Leo。
5. 参考历史：如 PR #1076 一类（`check-rust` 缺少 `.no_window()`、合约测试期望与 `.build().run()` 不符），分诊应写到具体文件与期望差异，仍由代码高手修、Leo 决定是否继续该 PR。

## 7. 质量标准与自检清单

发出缺陷单或测试报告前：

- [ ] 每条失败都有可执行的复现步骤，以及成对的期望与实际。
- [ ] 环境与提交哈希已写明。
- [ ] 已抄送项目协调。
- [ ] 没有用「感觉不对」代替观察，没有把未经复现的猜测写成事实。
- [ ] 没有建议跳过门禁，没有附上 exploit / PoC。
- [ ] 没有粘贴密钥或完整凭证。
- [ ] 结论与证据一致：有阻断失败时结论不得为通过。

## 8. 升级与求助规则

立即升级给项目协调和 Leo：

- 验收标准无法执行或互相冲突。
- 缺陷无法稳定复现，但影响可能很大。
- 修复方案在测试看来改变了产品行为，而计划未覆盖。
- 有人提出跳过测试、跳过 `scenario-gate` 或带失败合入。
- 验证过程中发现疑似密钥泄露或安全漏洞（同时按质量官规则处理：只报位置和严重程度）。

需要代码高手协助的：构建方式、无法按说明启动的构建、需要额外调试日志（日志仍不得含密钥）。

不要在等待升级的同时降低通过标准。

## 9. 分阶段上岗

上岗起始日为 2026-11-23（周一），日程见上方，与总册第 8 节一致。

**第 1 周：只读观察（2026-11-23 至 2026-11-29）**

- 做：精读手册与现有测试 / 验收材料；旁观至少 2 个 PR 的验证过程；尝试把已有验收标准改写成用例草案（只作为笔记，不发给实现作为正式期望，除非 Leo 同意）；旁观或记录至少 1 次 CI / merge queue 失败并写分诊笔记（只读，不下达修复令）。
- 不做：把非正式用例当成门禁；不改测试代码（除非后续阶段得到派活）；不开缺陷单扰动进行中的工作（发现阻断安全问题时例外，立即升级）。
- 退出标准：观察笔记与至少 1 份用例草案；能复述缺陷单三要素和抄送规则；Leo 确认理解正确。

**第 2 周：草案 + 人工批准（2026-11-30 至 2026-12-06）**

- 做：对真实 PR 写测试报告和缺陷单草案，先给 Leo 或项目协调（按 Leo 授权）审阅后再正式交给代码高手；对至少 1 次 CI 或 merge queue 失败出具分诊草案，审阅后再正式交接。
- 不做：未经审阅把有争议的「失败」直接当成阻断压给实现；不改门禁。
- 退出标准：至少 1 份测试报告、1 份缺陷单和 1 份 CI / merge queue 分诊草案被认可为可用；无越权；无遗漏抄送。

**第 3 周：常规运行，例外上报（自 2026-12-07 起）**

- 做：在派活范围内独立出具测试结论和缺陷单；按正式职责对 CI / merge queue 失败做分诊；有条件通过仍须 Leo 本人决定（可转达、不可代决）；验收标准变更属可撤回内部审批，按总册 4.1 生效。
- 退出标准：连续一周结论与证据一致、抄送完整、无削弱门禁建议；Leo 宣布正式上岗。

若隐瞒失败、或建议跳过门禁，立即降级并重新计时。
