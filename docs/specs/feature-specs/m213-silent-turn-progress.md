# M213：长回合的「沉默」可见化（首个可见 token 看门狗）

状态：规格（待实现）。本文件先固化 2026-10-31 的现场诊断、结论与验收口径，代码改动单独按本文要求实现。

## 1. 用户上报的现象（逐字保留）

> 没有，还是这么慢，你知道上次出现模型一直没有停下来 思考了九分钟 然后停在think 2. 换成codex之后 模型以为项目用subagent跑 跑到现在还在跑
>
> 关键我又没有开1m上下文 为什么性能还是这么差 为什么可以思考这么久 你能优化下么

可观测事实（用户视角）：

1. 一个回合从提交到「出现第一个可见字符」可能长达 9 分钟；
2. 这段时间里界面只有 thinking 块在长，没有文本、没有工具结果、没有失败原因；
3. 用户看到的是「没停下来」，而不是「在做什么」。

## 2. 现场排查结论（本仓库取证）

| 结论 | 证据 |
| --- | --- |
| 9 分钟静默**不是** M212 日额度上限造成的阻塞 | M212 只在 `agent/failover.rs` 的路由判定里生效，命中上限进入 `waiting_wake` 并给出等待原因；它不在 SSE 首 token 的关键路径上，也不会让回合停在无输出状态 |
| M212 是**已合并并已发布**的产品能力（v1.91.66/67 之后的批次） | `git log` 中 `feat/fix M212` 合并提交；把它在本分支回退会构成 `src-tauri/src/agent/daily_spend.rs`、`src-tauri/src/commands/costs.rs` 这两个产品文件相对 `origin/main` 的未映射改动，`tools/governance/run_scenario_harness_gate.py --stage local` 直接 fail closed |
| 因此本次**撤销**了「回退 M212」的实验性改动 | 回退后工作树恢复干净，本地门禁 `scenario-harness-gate: OK`。是否下线 M212 属于产品决策，必须由用户明确批准，并由实现方补场景映射，不得夹带在性能修复里 |
| 桌面回合在「交互模式」下没有墙钟预算 | `agent/mod.rs::autonomous_budget_denial` 对桌面传入 `None` 墙钟（slice 4.8c b3），交互模式下用户本人在场，设计上不硬杀回合；代价是**没有任何机制把静默变可见** |
| 真正的可优化点是「静默不可见 + 无进度要求」 | 9 分钟里模型在连续做推理与工具调用，但没有任何一处要求它在长时间无文本后给用户一行进度，也没有事件把「已运行多久 / 调用了多少工具」送到界面 |

结论：这是**可观测性与回合节奏**缺陷，不是上下文长度或 M212 的缺陷。把它当作「上下文太大」去调参会继续无效。

## 3. 设计（实现方按此落地）

### M213-1 首个可见 token 看门狗（保命线）

- 回合开始记录 `turn_started_at`，以及 `assistant_text_bytes` 与 `tool_call_count`。
- 每 `HEARTBEAT_INTERVAL`（建议 15s）评估一次；当「自上次可见文本以来」超过 `SILENT_PROGRESS_AFTER`（建议 45s）且本回合 `assistant_text_bytes == 0` 或静默期超阈值时，向界面发一条进度事件，携带：
  `silent_secs`、`tool_call_count`、`current_phase`（推理 / 等待工具结果 / 等待上游响应）。
- 界面必须把它渲染成一行可见文字（例如「模型仍在处理：已 1 分 05 秒，工具 7 次」），**不得**只用来刷新 spinner。用户能区分「在干活」和「卡死」是这条的全部价值。
- 硬阈值 `SILENT_WARN_AFTER`（建议 180s）：无任何 token 且无工具返回时，发一条警告级事件，保留回合，不静默。

### M213-2 长静默后要求一行进度（节奏）

- 当同一回合连续 `QUIET_TOOL_ROUNDS`（建议 12）次工具调用没有产生任何可见文本时，在下一轮系统提示里追加一条要求：先用一行文字说明当前进展与下一步，再继续调用工具。
- 这条提示与既有 `事实纠偏` 纠偏同类：只改变措辞要求，不改变权限、门禁与工具集。

### M213-3 证据与日志

- 每个回合结束写一条结构化记录：`ttft_ms`（提交 → 首个可见 token）、`max_silent_ms`、`tool_call_count`、`progress_events`。
- 该记录进入现有 trajectory/日志通道；不记录消息正文、凭据或生产数据（Observation Harness 边界）。

## 4. 非目标

- 不缩短上下文窗口，不改 `1M context` 相关开关。
- 不给交互模式加墙钟硬终止（用户在场，终止权在用户）。
- 不回退 M212；M212 的去留是独立的产品决策。
- 不修改 `.github/` 工作流、场景注册表与校验器。

## 5. 验收（机器可检）

| 追踪项 | 检查 |
| --- | --- |
| M213-1a | 纯函数 `silent_progress_notice(silent_ms, tool_calls, has_text)`：静默未超阈值返回 `None`；超阈值返回含秒数与工具次数的文案；已有可见文本的超长静默也返回文案 |
| M213-1b | 回合内注入合成时钟驱动看门狗，断言至少发出一次进度事件，且事件字段与注入时钟一致（不是打印对比） |
| M213-1c | `SILENT_WARN_AFTER` 之后无 token 的合成回合发出警告事件且回合仍可继续 |
| M213-2a | 连续 `QUIET_TOOL_ROUNDS` 次无文本工具调用后，下一轮系统提示包含进度要求；`QUIET_TOOL_ROUNDS - 1` 次时不含 |
| M213-3a | 回合结束记录含 `ttft_ms` / `max_silent_ms`，且断言记录中不含消息正文 |

## 6. Harness

- Spec Harness：本文即规格，追踪项 M213-1/2/3 对应第 3 节。
- Observation Harness：只记录时长、计数与阶段名；禁止正文、凭据、生产数据。
- Compatibility Harness：不改变额度、时段、权限与工具集语义；`waiting_wake`、`PROVIDER_FATAL` 等既有终态不变。
- AI Collaboration Harness：范围限「静默可见化」；假设（静默阈值取值）由合成时钟测试验证；复核点为进度事件是否真的可见、警告是否只发一次。
- Release Harness：性能与可观测性缺陷，落地后可随下一次 `fix` 批次发版。
