# 信任模式下不再询问会话自己工作区内的操作，未应答的请求等待而不是让任务失败（CF-TPP，含 M1）

## 背景与用户决策
信任模式意味着「用户信任 agent 在本任务自己的工作区内做它需要做的事」。影响外部世界或用户自身数据的操作仍然需要确认。等待确认期间，任务不能因为用户离开一会儿就失败。

## 决策
在信任模式下，效果完全停留在会话自身受管工作区内的操作不再弹确认。超出工作区的操作保留现有确认。确认请求绝不会因为没人在场而被静默作废或记成「用户取消」；用户回来后仍然可以批准它，任务继续。

## Applicable Harnesses
Spec Harness；Viewport Harness（授权弹窗、等待状态、light/dark）；AI Collaboration Harness（触碰安全边界：PR 必须列出每一条决定「是否弹窗」的被改规则；R2 的反例测试是审查点之一）。

## 测试矩阵
- 信任模式：工作区内删除/覆盖/运行 → 无确认。
- 反例（任何模式）：工作区外、主 checkout、`..` 逃逸、符号链接逃逸、凭据、系统设置、直接推送默认分支 → 仍然确认/拒绝。
- 标准模式：现有行为不变。
- 无人应答：请求长时间保持打开；之后批准时任务自行接着执行；拒绝 → 任务用大白话解释并停止该操作。
- 视口：信任/标准模式下的弹窗、等待状态、light/dark。

## 约束
- 这是安全边界：不得放宽任何工作区外的自动放行规则。若发现现有规则应当放宽，写成 Spec Amendment 交由用户决定；不要自行更改。

## 实现说明（不改变任何需求或验收标准）
- R3 在本期实现为：`PermissionDialog` 在 `trusted` 时不再渲染「信任本会话并允许」按钮，保留一句说明该操作仍被拦截的提示；`trusted=false` 的标准模式行为不变。
- R6 的会话侧修复为：会话重新加载（`selectSession`）时不再把该会话内存中的 `pendingPermission` 覆盖成 null（`src/stores/chat.ts` 的水合合并逻辑），使「切走再切回」仍显示同一条未过期请求；侧栏对 `runtime[id].pendingPermission != null` 的会话显示「等待批准」标记。
