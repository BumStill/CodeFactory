# M264：合并后的清理交给系统做，会话不再为此要审批

## 现场（2026-11-07 到 11-08）

最近每单（M257 到 M263）在合并后都至少要一次审批，内容几乎都是同一件事：

- `git push origin --delete <本会话已合并的分支>`（`trusted.git.unproved`）
- `rm -rf .codefactory-cache/cargo-target-<task>`（`shell.safety: recursive rm`）

这些是任务模板 §8 要求的收尾动作。系统收尾其实已经会删已合并的远端分支（例如
c5b6a28e 的结束原因写着「已删除已合并远端分支」），但会话并不知道，还会自己再做一遍。

## 规格（Requirements）

- **R1**：PR 合并后，系统收尾负责清理这一单留下的东西：
  - 本会话 PR 的远端分支：PR 已 merged，且分支名与本会话 `thin_delivery_refs`
    记录（同一 `pr_number`）一致时才删；
  - 托管工作区里本单的构建目录：`.codefactory-cache/cargo-target-*`，以及工作区
    内其它带 `CACHEDIR.TAG` 或 cargo 指纹结构（`.rustc_info.json` / `.fingerprint`）
    的目录。
  全部走现有的工作区边界（`CloseoutTarget.worktree`），不碰工作区以外的东西，也不碰
  共享缓存 `.codefactory-cache/cargo-target`（共享缓存由 CF-BUILD 预算管理）。
  符号链接一律跳过——`src-tauri/target` 通常就是指向共享缓存的链接。
- **R2**：清理结果写进结束原因，复用 M259/M262 的逐项核对格式：已做的写
  「已由系统删除 / 已清理」，没做或失败的写「未清理：<原因>」，无法核对的仍写
  「未核验：<原因>」。
- **R3**：会话收尾时，如果分支和构建目录已经由系统删掉，它用到的命令不应报错；如果
  会话仍尝试删除，审批规则不变（不放宽任何审批）。因此系统清理结果必须写进结束
  原因，并把「已清理」这件事交给会话可见的收尾事实，而不是要求会话再去执行命令。
- **R4**：工作区有未提交或未推送的改动时，不删任何东西（分支、构建目录都不动），
  并在原因里写明「未清理：工作区还有未提交改动 / 还有 N 个提交没有推送」。
- **R5**：任务模板 §8 应改为「会话只核对、不动手删」：合并后由系统收尾清理远端分支
  与构建目录，会话只需从结束原因里确认清理结果，不再执行 `git push --delete` 或
  `rm -rf`；模板由编排方修改，本仓库只记录结论。

## 判定顺序（实现约束）

1. `git fetch --prune <remote> <default_branch>`，再判合并提交是否在默认分支
   （M262：优先用 PR 真实合并提交编号）。
2. 读工作区状态：未提交改动、未推送提交。
3. 有任一阻塞项（合并未确认、有未提交改动、有未推送提交）→ 一律不删，逐项写
   「未清理：<阻塞原因>」。
4. 无阻塞项 → 先删本会话远端分支（仅当分支名来自 `thin_delivery_refs`），再清理
   构建目录；每一步的真实结果写进原因。

## 测试

- 真实裸远端 + 真实 DB：PR 合并后，系统删除远端分支和任务构建目录，共享缓存保留，
  结束原因写清楚。
- 工作区有未提交改动：分支与构建目录都不删，原因写清楚。
- 分支名不是本会话 `thin_delivery_refs` 记录的（无交付记录）：远端分支不删。

## 验收（真机，编排方发版后做）

下一单合并后，全程没有删分支和删构建目录的审批，结束原因写着已清理。
