# CF-BUILD：编译缓存有上限、跨任务复用、任务结束即回收、少写盘

## 背景与用户决策

用户 2026-10-10：「要系统性的解决这种问题，不仅仅是磁盘占用问题，还要考虑磁盘频繁读写问题。」
编译产物可以重建，但不能无限增长，也不能每个任务重复写一遍。

证据（2026-10-10）：

- 10:02 磁盘只剩 1.5 GB（100%），M51 会话编译 Rust 时报磁盘写满中断。
- 主 checkout 下的 `.codefactory-cache/cargo-target`（仓库 `pnpm cargo:shared` 和 worktree 自动链接共用的编译目录）自 2026-07-17 建立后从未清理，涨到 410 GB：
  - `debug/deps` 277 GB / 48.6 万个文件，其中 35.6 万个超过 14 天没被访问；
  - `debug/incremental` 201 GB，光主库一个 crate 就有 183 份增量会话；
  - 原因：各 worktree 路径不同，同一份项目代码在共享目录里会产出互不复用的产物，旧的永不淘汰。共享实际只对第三方依赖有效。
- 主 checkout 下另有 10 个任务专属编译目录（每个 5.7–12 GB），最后写入是 08-11/12，闲置两个月。
- 托管工作区里每个任务的专属编译目录 7.6–16 GB；任务提前死亡、失败或停止时永不回收，10-10 累计 160 GB。
- 用户 10-10 自查：项目里 11 个 Rust 调试缓存目录合计约 509 GB。
- 写盘：每个新任务都从零编译全部第三方依赖（单次写入 6–16 GB）；3 个任务并行时同时满负荷写盘；增量编译数据每次构建都整体重写。
- Claude 手动清理过两次（10:02 腾出 120 GB；10:2x 清掉 410 GB 共享目录和 10 个闲置目录）。这件事需要产品自己做。
- 历史教训：并行 worktree 共用同一个编译目录时出现过串扰，报错引用的符号在当前源码里根本搜不到。

## 决策

CodeFactory 产生或管理的编译缓存（托管工作区里的，加上本仓库开发工具用的共享目录）作为一个整体来管：

- 有总上限，按「最久未使用」淘汰；
- 任务一结束就回收；
- 第三方依赖只编译一份，各任务复用；
- 单次构建的写盘量，以及同时进行的重型构建数，都受控；
- 正在用的缓存永不删除。

本期必须覆盖 Rust。设计上不限于 Rust，其他语言的依赖或产物目录以后可以接入同一套管理。

## Requirements Traceability

| Req ID | 需求 | 最低证据 |
| --- | --- | --- |
| CF-BLD-R1 | **总上限**：所有编译缓存合计不超过一个上限（默认值自定，PR 里说明理由；可在设置里改）。超限时先淘汰最久未使用的；正在构建的缓存、所属任务还能继续的缓存，一律不淘汰 | 合成目录测试：超限后淘汰顺序正确，使用中的不动；真机连续使用一周后总量仍在上限内（Claude 验） |
| CF-BLD-R2 | **任务结束即回收**（原 CF-CLO-R8）：任务以完成、失败或停止结束后（不只是合并后），它专属的编译产物在有界时间内被清掉；运行中或还能继续的任务不动 | 测试：三种终态都会被清，运行中的不动 |
| CF-BLD-R3 | **磁盘守卫**（原 CF-CLO-R9）：开始新任务或新构建前检查剩余空间。低于阈值（默认值自定并说明理由）时先清闲置缓存；还不够就用大白话告诉用户「空间不足，已清理 X，还差 Y」并暂停，而不是编译到一半报磁盘满 | 测试；文案通过内部词汇守卫 |
| CF-BLD-R4 | **占用可见、可一键清理**（原 CF-CLO-R10）：用户能看到工作区和编译缓存各占多少空间，一个操作就能清理；后台入口也能调用（符合「可后台操控」默认要求） | 组件测试 + 后台入口测试 |
| CF-BLD-R5 | **第三方依赖只编译一份**：同一工具链、同一编译选项下，新任务的首次构建复用其他任务已经编好的第三方依赖，不从零重编。并行任务不会因为争同一把锁互相长时间阻塞。共享不得造成跨任务串扰：一个任务的构建结果不会混进另一个任务 | 实测：第二个任务首次全量测试构建时，第三方依赖重编比例 ≤ 10%（PR 写实测数）；两个任务并行构建，锁等待不超过上限（自定并说明）；串扰反例测试 |
| CF-BLD-R6 | **单次构建少写盘**：一次全工作区测试构建的写盘量和产物体积，比改前基线至少降 50%（PR 记录改前、改后实测）；测试失败时依然能看到带文件和行号的调用栈 | 改前/改后实测数据 + 失败用例的行号断言 |
| CF-BLD-R7 | **重型构建限流**：整机同时进行的重型构建（编译、全量测试）有数量上限（默认值自定，说明理由）。超出的排队，并显示「等待编译空位」这类用户看得懂的状态。排队不算失败、不消耗自动恢复次数、不会死锁 | 测试：发起「上限 + 1」个构建，1 个排队并按顺序放行；排队期间恢复计数不变 |
| CF-BLD-R8 | **存量清理**：升级后对已有缓存按 R1、R2 执行一次（包括主 checkout 的共享目录和历史任务目录），不碰使用中的；不碰用户主 checkout 的源码，也不碰 app 没创建的目录 | 混合状态的合成数据测试；升级后真机检查一次（Claude 验） |
| CF-BLD-R9 | **本仓库开发工具保持一致**：仓库自带的共享编译命令和 worktree 自动链接遵循同样的上限与淘汰规则，不再无限增长；仓库文档（AGENTS.md「Worktree 生命周期与 Cargo 缓存」一段）同步更新 | 测试 + 文档 diff |
| CF-BLD-R10 | **可追溯**：每次淘汰或回收都记录清了什么、多大、为什么、谁触发的；每个任务产出的编译缓存大小可以查到 | 测试：断言审计记录的各字段 |

## 测试矩阵

- 正常：
  - 两个任务先后构建，第二个复用第三方依赖；
  - 超过上限时淘汰最久未使用的。
- 边界：
  - 构建进行中触发清理，正在用的不动；
  - 任务失败或被停止后，缓存被回收；
  - 剩余空间低于阈值时，先清理再开始，不够就明说并暂停。
- 并发：发起「上限 + 1」个构建，多出的排队，恢复计数不变；并行构建不串扰。
- 存量：新旧混合、使用中与闲置混合的目录。
- 中断：清理到一半 app 退出，下次启动接着清完，不留半截状态。
- 基线：改前、改后的体积、写盘量、依赖重编比例都实测记录。

## 约束

- 改编译配置（profile 等）属于构建配置变更：PR 必须写风险说明，并且先测改前基线再改。
- 不改 `.github/` 下的工作流；CI 有自己的编译目录，不在本任务范围内。
- 托管工作区目录本身的删除归 CF-CLOSEOUT（合并后收尾），本任务只管编译缓存；两边重叠的「任务何时算结束」判定，与 CF-CLOSEOUT、U26 保持一致；碰到同一处逻辑时改动最小化，并在 PR 里写明重叠。
- 其余约束同模板。

## Implementation Notes

（技术约束，不改变任何需求或验收标准；实现过程中补充。）

- 缓存根集合（`BuildCacheRoot`）：`<app_data>/execution-workspaces/*/.codefactory-cache/*`（任务专属）与
  `<repo>/.codefactory-cache/cargo-target*`（本仓库开发工具共享目录）。
- R1 默认上限 60 GiB：足以容纳一份热共享缓存（实测冷全量构建约 6–16 GiB）加上数个活跃任务目录，
  同时远低于改前实测的 509 GiB；R3 默认低水位 20 GiB。
- R7 默认重型构建并发上限 2：3 个并行构建是旧故障的直接诱因（同时满负荷写盘），
  而单机构建受 CPU 与磁盘带宽限制，超过 2 个只会互相拖慢。
- CARGO_TARGET_DIR 分两层：共享缓存目录只放可跨任务复用的第三方依赖与最终产物，任务私有目标目录按 workspace 路径分桶
  （`task_target_dir`），并通过 `CARGO_INCREMENTAL=0` 关闭增量产物，避免 worktree 路径不同导致的产物互不复用与重复写盘。
