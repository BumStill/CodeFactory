# M252：工作区分配忙与过期模型等待

## 规格（任务原文）
- R1：仓库分配锁被占时，这是系统自己的等待。用户消息保留，按退避自动重试，不进入 `waiting_user`，不要求用户操作。重试次数有上限，上限按真实次数算；到上限后写明真实失败原因和用户消息还在。
- R2：先查清 11-06 是谁占着锁，把结论写进规格。如果锁在重启后还由旧进程持有，修回收逻辑。
- R3：任何工作区失败都不再说「请检查模型凭据」。只有真实的凭据失败才这么说。
- R4：一次模型调用成功后，清除该会话的 `model_availability_waits`，并取消因它产生的 `model-availability-*` 唤醒。其它唤醒不再沿用已过期的恢复时间。
- R5：不新增用户可见的中间态。

## 测试（任务原文）
- 真实 DB：锁被另一个存活进程持有时，发送消息不进入 `waiting_user`；锁释放后自动开始回合，且只开始一次。
- 上限：一直拿不到锁时进入明确结果，用户消息不丢。
- R3：工作区失败的文案不含「凭据」。
- R4：等待行在调用成功后被清除，界面状态不再显示过期原因。

## 验收（真机，编排方发版后做）
升级重启后立刻发消息，会话自动开始，不出现「请检查模型凭据」。

## Implementation Notes

### R2 现场调查
- 只读查询当前真实 DB 和 11-06 的独立 SQLite 备份：备份内仓库分配锁为空，未发现持久记录 lock acquire/release 的审计事件。因此无法从现存证据精确追溯 11-06 瞬时锁的原始持有人；不把当前锁或失败请求的进程误认为历史持锁人。
- 当前 DB 实际观察到 `workspace-cleanup:<pid>:<start-token>` 格式的分配锁。代码确认它来自 `run_cleanup_pass_with`；旧回收函数直接把首段解析为 PID，遇到 `workspace-cleanup` 会跳过，导致旧清理进程退出后仍等待 300 秒租约。
- 已修复清理前缀解析，继续用 OS PID + start token 判活；检查失败仍保守保留存活锁。回归分别覆盖存活清理锁、旧 start token、已退出普通进程。
