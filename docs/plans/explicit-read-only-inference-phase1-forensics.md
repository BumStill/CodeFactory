# 只读推断取证：`is_explicit_planning_request` 第一阶段结论

状态：**取证完成（一/二/三/四全部完成，方案按用户口径修订），方案待定；未改任何产品代码**
范围：`src-tauri/src/agent/dispatch.rs` 的 `is_explicit_planning_request` 及其调用链
（`decide_chat_contract` / `steer_capability_override*` → `TurnCapability::ReviewOnly`）

## 0. 结论摘要

1. **判定面几乎全是误伤。** 生产库 576 条 `role=user` 消息里，28 条被判为整轮只读；
   人工逐条复核后，只有 **5 条（18%）真是整轮只读意图**，其余 **23 条（82%）是执行请求里的
   局部或条件约束**（其中多数还带着「跑测试/交付/修复」这类明确动作）。
2. **2026-09-24 的事故在库里可直接复现。** 该回合主体是「合并 origin/main → 跑 cargo test →
   以同样参数调用 `deliver_changes`」，末尾一句针对假设情形（CI 再遇到环境抖动）的
   「不要改代码或验收脚本」命中词表里的两个字子串，整轮 `capability` 被压成 `ReviewOnly`。
3. **历次修不好是同一个原因：修在同一维度上。** 判定始终是「整句 `contains` 一个短语 → 整轮撤写权限」，
   历次改动只是在词表/白名单里加项或加例外（§3）。判定里**没有「约束作用域」这个概念**，
   所以「限制某一部分」和「撤销整轮」在结构上无法区分。
4. **业界没有人从措辞推断写权限**（§4）。整轮/整会话只读一律是用户显式持有的开关
   （Claude Code 的 permission mode、Codex 的 `sandbox_mode`、Cursor 的 Ask/Plan、Aider 的 `/ask`）；
   「某部分别动」要么是给模型的指令，要么用**显式结构化路径规则**表达（`Edit(docs/**)` 的 deny/ask、
   `writable_roots`、`/read-only` 逐文件）。
5. CodeFactory 不向用户暴露「计划/执行」模式开关（产品原则）。因此修订后的方案是：
   **整轮只读只由整轮句式/任务类型的显式声明触发；措辞里的局部约束只作为给模型的指令，
   并在回合里回显便于审计；工具层强制只来自显式来源。** 把「某部分别动」解析成本轮路径拒绝规则
   仍然是从措辞推断写权限（只是范围更小、解析错了照样拒掉合法写入），因此只保留为**备选方案、不作推荐**（§5）。

更正一处早先的推断：28 条命中里有 15 条是「只读审查」子 agent 任务书，但它们**不是运行时事实**。

真实缺口是另一个：委派路径此前没有任何结构化只读来源，「只读审查」任务书只能靠模型自觉；

### 三条共同模式 → 对照到本问题的口径

1. **整轮/整会话只读 = 用户显式持有的开关。** 对照结论：CodeFactory 不暴露计划/执行模式开关
   （产品原则），所以这里的「显式开关」只能由**任务类型或回合结构**承载：子 agent 任务书自带的
   只读声明、验收/`E2E` 场景自带的只读声明，都是用户（或其代理）显式给出的，而不是从措辞猜的。
2. **局部约束 = 给模型的指令，或用显式结构化路径规则表达。** 对照结论（按用户口径收紧）：
   措辞里的局部约束**只走指令通道**（注入 + 回合内回显），**不进工具层强制**；
   工具层强制只来自显式来源（显式规则 / 任务类型声明）。
3. **四家都不从措辞推断写权限。** 对照结论：`is_explicit_planning_request` 必须停止作为
   写权限的唯一来源；语气/措辞只能决定**给模型的指令**，不能决定能力，也不能决定工具层拒绝。

## 5. 设计方案（按三条业界模式与用户口径修订）

共同的硬性前提（所有方案都必须满足）：

- 不新增词表条目、不新增正则；
- 两条护栏测试断言**原样**保留：
  `the_hard_read_only_gate_comes_only_from_an_explicit_user_constraint`、
  `the_field_report_message_can_now_reach_the_edit_it_was_denied`；
- 不新增任何用户侧「计划/执行」模式开关；
- 措辞解析的产物**不得**成为工具层强制（硬拒绝）的来源。

### 方案 1（推荐）：整轮只读只认整轮句式；局部约束降级为指令并回显

**1a. 判据重构（结构判据，取代短语判据）**

一个回合被判为整轮只读，当且仅当同时满足：

1. 该回合**存在**只读意图措辞（保留现有 `PLAN_ONLY_*` 仅作「信号存在性」检测，不新增条目）；
2. 该回合**不存在任何**执行/交付/变更动作意图（`is_direct_execution_request`、
   `is_delivery_request`、`is_change_request` 皆为假）；
3. 该回合**不存在**「只读措辞被条件从句或具名对象限定」的结构迹象——只读措辞不与条件标记
   （假设情形）或具名对象同处一个分句。

不满足 1–3 任一条时，`is_explicit_planning_request` **不得**撤销整轮写权限。

**1b. 局部约束的处理（指令通道）**

- 解析出的「不要改⟨对象⟩」「如果⟨条件⟩就别动⟨对象⟩」只作为**回合级指令**注入本轮上下文，
  且必须在回合内**回显**（用户能看到「本轮已把 X 作为约束告知模型」），便于审计与事后归因；
- **不**产生工具层拒绝规则、**不**进入 policy 的拒绝判定；
- 模型若仍改了被点名对象，后果由回显 + 会话记录暴露，而不是靠工具层假装确定。

**1c. 工具层强制的唯一来源（显式来源，与本方案正交）**

工具层强制只允许来自显式声明：子 agent 任务书中的只读声明、`E2E`/验收场景声明、
用户显式给出的结构化规则。这些来源是**任务类型/显式规则**，不是从措辞推断。

- **与业界异同**：同——整轮只读由显式声明承载，局部约束只作指令，不推断权限
  （模式 1/2/3 全满足）；异——Claude Code/Codex 的整轮只读是**用户在界面或配置里持有的开关**，
  CodeFactory 不暴露该开关，因此把「开关」的位置让渡给「整轮句式 + 任务类型声明」。
  局部约束这一层，四家都有「指令」通道，而「显式路径规则」这一层 CodeFactory 目前没有用户入口，
  本方案选择**不补一个新入口**（否则等于新增模式开关），只保留指令通道。
- **是否放宽硬只读门禁**：不放宽。门禁来源反而**收窄**（从「出现子串」到「整轮只表达只读」）。
- **低遵从度模型风险**：中。约束只作指令时，`deepseek-v4-flash` 这类模型可能改到被点名的对象。
  缓解：约束作为**回合级显式约束块**注入（不依赖模型记忆）+ 回合回显（用户可立即发现）；
  **明确不把这种风险转成工具层硬拒绝**，因为那会把风险换成 §2/§5-备选 里的误拒停摆。
- **回归测试（先看到红）：**
  1. 交付请求 + 条件性只读措辞（合并 → 跑测试 → 交付 +「如果 X 就别改 Y」）→ 能力**不得**为 `ReviewOnly`；
  2. 裸只读句（无任何动作意图）→ 仍为 `explicit_read_only` / `ReviewOnly`（护栏 1 原样）；
  3. 子 agent 任务书（「只读审查…运行必要的聚焦测试并返回证据」）→ **不得**降级，测试与证据可产出；
  4. 局部约束在回合内**有回显**，且**未**产生任何工具层拒绝（断言无拒绝事件）。

### 方案 2（备选，不推荐）：把措辞解析成当轮路径拒绝规则

在方案 1 之上，把「不要改⟨对象⟩」里的具名对象解析成路径集合，由工具层对
`edit_file` / `write_file` 命中时确定性拒绝。

- **为什么不推荐（用户口径）**：这仍然是从措辞推断写权限，只是范围小一些；解析错了照样会拒掉
  合法写入，而「一句话对应哪些文件」本身就是猜。业界两种做法里，措辞里的局部约束只作指令，
  硬拒绝只来自用户显式的结构化规则。
- **误解析概率（用本次取证做实证）**：被判只读的 28 条里 **23 条（82%）是执行请求中的局部/条件约束**，
  它们本轮都有合法写入；把这类措辞解析成拒绝规则，就会拒掉本轮该做的事。
  反向误差（该拒未拒）无法给出下界：只读措辞点名的对象常是自然语言（「验收脚本」「这个文件」），
  到路径的映射本身不唯一。因此误拒与漏拒都不可界定，无法作为权限闸门。
- **被拒后的出路（必须写清，否则错误直接停摆整轮）**：确定性拒绝无法被模型绕过，因此必须提供
  （a）用户在回显条目上显式取消该约束（本轮内即时生效），或（b）拒绝即失败并把控制权交回用户。
  缺少出路的版本等价于把本次事故换成另一种停摆。
- **回归测试（若真要实施）**：受控路径拒绝 / 非受控路径放行；约束在回合结束即失效；
  误拒场景存在可恢复路径（取消约束后重试成功）；护栏 1/2 原样；交付续接回合走通。
- **结论**：作为对照与「确有强诉求时」的讨论材料保留，**不作为推荐方案**。

取舍对比：

| | 是否放宽硬只读门禁 | 是否从措辞推断权限 | 低遵从度模型风险 | 误拒风险 | 改动面 | 新增用户侧开关 |
| --- | --- | --- | --- | --- | --- | --- |
| 方案 1（推荐） | 否（来源收窄） | 否（措辞只作指令） | 中（靠回显 + 约束块缓解） | 无（不产生拒绝） | 小（单点判据重构 + 指令通道 + 回显） | 无 |
| 方案 2（备选） | 否 | 是（范围更小） | 低 | 高（82% 实证误伤面） | 中（约束通道 + 工具层校验 + 审计） | 无 |

**推荐路径**：实施方案 1；方案 2 仅作为备选记录。
