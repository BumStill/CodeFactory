# 分析：CodeFactory 撞 GitHub 限流，是产品设计问题吗

> 状态: **分析报告**（不是待批准方案；末尾附建议）
>
> 日期: 2026-08-05
>
> 数据源: `~/Library/Application Support/com.codefactory.app/codefactory.db`，近 7 天 `tool_calls`

---

## 一句话结论

**主因不是产品设计，是 agent 的行为模式——但产品有一个真实的设计缺口在纵容它。**

`deliver_changes` 自身的 API 用量是克制的（有退避、有上限）。真正把配额打穿的是
agent 绕开这条受管路径、直接用 bash 跑 `gh ... --watch` 和 `until` 轮询循环。产品
对这条旁路**没有任何约束**。

限流实际发生在 **08-03 / 08-04**，正是 `--watch` 集中出现的两天。

### 为什么 `--watch` 是放大器

`gh pr checks --watch` 会自行输出 `Refreshing checks status every 10 seconds.`——
**一次调用 = 每 10 秒一次请求，直到 CI 结束**。本仓库 `check` job 约 10–16 分钟：

```
单次 watch ≈ 60–96 次请求
08-04 的 13 次 watch ≈ 800–1200 次请求
```

而 `tool_calls` 表里它只记为 **1 行**。所以「每天才 62–138 次 gh 调用」这个表面数字
完全掩盖了真实用量——**这也是为什么问题一直没被看见**。

### 对照：产品自身的受管路径是克制的

`deliver_changes` 的 CI 轮询（`delivery.rs`）：

```rust
// polling is the biggest API cost of a delivery run; a fixed 10s cadence
// burns ~30 requests for a 5-minute CI. Backoff keeps the first polls
let mut interval = 10u32;
...
interval = (interval * 2).min(60);
```

10s 起、翻倍、60s 封顶。一次 10 分钟 CI 约 **13 次**请求，而不是 60 次。

仓库还已经做过第二道加固：把 live gh smoke 改成 `CODEFACTORY_RUN_GH_SMOKE=1` 显式
开启，注释写明「默认 Rust 套件在交付和 CI 中频繁运行，打活 API 会把 PR 轮询放大成
限流」。

**也就是说：受管路径被认真优化过两轮，旁路一次都没管过。**

## 判定

### 不是产品设计问题的部分

- `deliver_changes` 的退避策略合理，13 次/交付的量级不可能打穿 5000/hr。
- 08-03/08-04 各 20/18 次交付 × ~13 次 ≈ 260 次，占配额 5%。

### 是产品设计缺口的部分

**产品提供了受管交付通道，却不阻止 agent 绕过它去裸调 `gh`。**

这不是假设——本仓库 AGENTS.md 已经明令「交付相关的提交/推送/合并/发布必须走
`deliver_changes`」，而且**确实有命令门禁在拦截 `git` 类操作**（本会话截图里出现过
「本地 Git 同步命令被仓库交付策略拦截」）。但：

- 门禁只拦**改状态**的操作（commit/push/merge），
- **不拦只读的 `gh pr checks --watch` / `gh run watch`**——它们不改任何东西，看起来无害，
- 而它们恰恰是配额消耗的大头。

于是形成一个盲区：**危险的写操作被管住了，昂贵的读操作完全放开。**

### 第三方原因（非产品）

本次限流有相当一部分是**我自己**造成的：我在等 CI 时用了多个并发 `--watch` 和
30–45 秒的 `until` 轮询，持续数小时。这是 agent 行为问题，不是产品 bug——但产品
没有任何机制阻止或提示它，所以又回到上面那个缺口。

---

## 建议（按性价比排序）

### 1. 把「昂贵的只读轮询」纳入现有命令门禁（最高性价比）

现有 shell 门禁已经能识别并拦截交付类命令，扩展它识别这几类：

| 模式 | 处置 |
| --- | --- |
| `gh ... --watch` | 拒绝，提示改用带退避的单次查询 + 重试 |
| `gh run watch` | 同上 |
| `until/while ... gh ...` 且 sleep < 60s | 拒绝或警告，要求间隔 ≥ 60s |

理由：这类命令**没有一个是必须的**——任何 `--watch` 都能用「单次查询 + 合理间隔重试」
替代，代价只是多写两行。而收益是消掉 90% 的配额消耗。

### 2. 暴露配额状态给 agent

在工具结果或系统提示里带上剩余配额（`gh api rate_limit` 很便宜）。agent 现在是
**完全盲飞**的——撞上 403 才知道，而那时已经晚了，还会连带把发布搞挂
（2026-08-04 auto-release 就是这么失败的）。

### 3. `deliver_changes` 提供「等待 CI」能力

agent 之所以裸调 `gh --watch`，是因为**受管工具没有提供等待能力**：`deliver_changes`
要么一路跑到 ceiling，要么返回 blocked，没有「帮我盯着这个 PR」这个中间态。
补上它，agent 就没有理由绕路。

**这条才是根治**：门禁是堵，这个是疏。只堵不疏的话，agent 会去找下一个旁路。

## 需要澄清的边界

本分析只覆盖 `com.codefactory.app` 这一个数据库（正式版）。`com.codefactory.dev`
等开发实例未纳入统计，实际总量可能更高，但**结论方向不受影响**——`--watch` 的
放大倍数是数量级的，其他来源难以与之相比。
