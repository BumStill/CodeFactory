# 排查：按「不允许任何形式的非业务阻断」原则审视交付链

> 日期: 2026-08-05
>
> 原则（用户 2026-08-05 明确）：**可以让人来决策关键业务判断，但不允许任何形式的非业务阻断。**
>
> 数据源: `~/Library/Application Support/com.codefactory.app/codefactory.db`，近 7 天

---

## 判据

仓库已有现成的分类 `RecoveryClass`，正好对应这条原则：

| 分类 | 是否算业务判断 | 按原则应有的行为 |
| --- | --- | --- |
| `UserActionRequired` | **是，但非必要不用** | 见下方「问人的门槛」 |
| `AgentActionRequired` | 否 | 必须自己修完继续 |
| `WaitRetryable` | 否 | 必须退避后自己续 |
| `ExternalStateUncertain` | 否 | 必须核实事实后自己续 |
| `None` | 否 | 不该出现在阻断路径 |

**凡是最终以 `blocked` 终止回合、而分类不是 `UserActionRequired` 的，都是违反原则的非业务阻断。**

### 问人的门槛（用户 2026-08-05 补充）

`UserActionRequired` 不是「可以随便停」的许可，它有三条附加约束：

1. **非必要不决策。** 用户已经表达「搞定」（例如去睡觉了）时，**按 agent 推荐的配置做完并记录**，而不是挂起等待。默认值由 agent 选，事后可审。
2. **不得频繁打断。** 同一件事反复回来问人，本身就是失败。
3. **不得降级要求。** 穷尽其他解法之前不许问；更不许把目标改小来让自己「完成」——
   例如请求 `through_release` 却停在 `pr_only` 然后宣称做完。**降级交付边界等同于没做完。**

因此真正允许停的只剩极窄一类：**缺少只有用户能提供的凭据/授权，且已经试过所有替代路径。**

## 实测：近 7 天 54 次交付中断

| 分类 | 次数 | 判定 |
| --- | --- | --- |
| CI 真失败 | 18 | **违反**——技术失败，应读日志修完继续 |
| `expect_branch` 声明过期 | 13 | **违反**——已修，见下 |
| 缺 live verifier | 8 | **违反**——配置缺失，应降级结论而非停 |
| 其他 | 8 | 待细查 |
| 等 auto-merge | 5 | **违反**——等待被报成阻塞 |
| 等待超时 | 2 | **违反**——超时应续等或换路 |

**54 次里没有一次是业务判断。** 全部是技术性、配置性或时序性的非业务阻断。

## 已修

### `expect_branch` 声明过期不再阻断（本 PR）

守卫原本假设「声明可信、cwd 可能漂移」。实测反了：两个并行 worktree **各自都声明了对方的分支**，而各自的 cwd 都是对的。

改为**以工作目录为准继续交付**，并把这次纠正记录成 `ok` 步骤。不丢防护：它当初要防的「在错分支上开出同名 PR」由 `conflicting_open_pr` 覆盖，那个比对真实标题与 head，不依赖调用方传来的字符串。

---

## 未修的系统性缺口（按严重度）

### ~~1. `MAX_ATTEMPTS = 2` 把可恢复失败转成终局~~（本 PR 已修）

`policy.rs::recoverable_delivery_prompt`：

```rust
const MAX_ATTEMPTS: u8 = 2;
if tool_name != "deliver_changes" || (!is_retryable_wait && attempts >= MAX_ATTEMPTS) { return None; }
```

返回 `None` → `blocked_tool_result = true` → 回合终止。

**一个需要修三次才能过的 CI 失败，会在第二次之后变成非业务阻断。** 这是当前最直接违反原则的一处。

**建议**：把上限从「固定次数」改成「**是否还在取得进展**」——每次尝试若产生了新的提交或不同的失败签名就继续；连续两次**完全相同**的失败签名才停。理由是次数无法区分「在修」和「在原地打转」，而失败签名可以。

### 2. 缺 live verifier 仍然进入阻断路径（8 次）

`#268` 已确立「缺执行器降级动作、缺验证器只降级结论」。live verifier 属于验证器，应当发布照做、只是不声称已上线。这 8 次说明还有路径没走到那条规则。

### 3. 等待类被计入阻断（5 + 2 次）

`WaitRetryable` 已有退避续跑机制，但仍有等待落到终局。需要确认这些是分类打错，还是退避次数耗尽后转终局——若是后者，与第 1 条同源。

### ~~4. 框架层的兜底提示仍是「不要重试」~~（本 PR 已修）

`run.rs` 在 `blocked_tool_result` 为真时注入：

> 「工具链已在明确边界停止。**不要重试**…请只用已有事实生成一次简洁阻断总结」

只要第 1 条还在，这句话就会在非业务阻断上生效，把「本可继续」硬变成「必须收工」。修完第 1 条后，这句话应当只在 `UserActionRequired` 时出现。

## 已修（第 1、4 条）

判据从「固定次数」改为「**失败签名是否变化**」：签名为
`{code}|{stage}|{reached_state}|{commit_sha}`，其中 `commit_sha` 是关键——推了修复就
说明 head 动了，下一次结论尚未可知，即便报错文字相同也算进展。**唯一的停是「同一个
失败在同一个 head 上原地重复」**。等待类永不终止：它的签名按设计就会重复，而推进它
的执行者是 GitHub。

终局提示同步改写，明说触发条件是「同一失败在未改变的 head 上重复，或需要用户提供
只有用户能给的输入」，并要求指出**需要用户做的那一件具体事**。

## 建议的下一步顺序

1. 第 1 条（上限改为按进展判定）——收益最大，直接消掉 CI 失败与等待耗尽两类。
2. 第 4 条（终局提示只对 `UserActionRequired` 出现）——与第 1 条配套，否则仍会误导。
3. 第 2 条（live verifier 路径补齐降级）。
4. 第 3 条与「其他 8 次」需要先取证再定性。

第 1、4 条动的是回合终止语义，属于核心控制流，建议单独一个 PR 并配回归测试，不要和本次的守卫修复混在一起。
