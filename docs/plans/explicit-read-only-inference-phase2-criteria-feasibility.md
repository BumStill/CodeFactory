## 1. 具体实现（照着写出来再跑的）

### 判据 2：零新增词，但只复用既有检测器


### 判据 3：零新增词版本只能用标点做代理

```text
criterion3(msg) = 对每个含只读措辞的分句：
                    分句去掉全部只读措辞后，不得残留任何字母/数字/CJK 字符
```

分句只用标点切分（`。！？；，、,.!?;` 与换行），判定只用既有 `PLAN_ONLY_*` 词表。

## 3. 三个决定性发现

1. **判据 2 救不了 9-24。** 那条消息里的动作是「合并 / 重跑 / 调用 `deliver_changes`」，
   `合并` 不在 `DELIVERY_CJK`（那里只有 `合并 pr`），`deliver_changes` 分词后是
   `deliver` + `changes`，而 `DELIVERY_EN_WORDS` 只有 `ship/release/publish/deploy/push/merge`。
   于是三个既有检测器一个都不触发（`fired=-`）→ `C2=T` → 仍判只读。
   要让它触发，只能往这些词表里加词，也就是第十一次加词。
2. **判据 2 还会被既有检测器自带的否定否决破坏。** `is_direct_execution_request` 只要发现
   任一 `NEGATIONS_EN` token 就返回 false。#1 那类「执行请求 + 局部约束」（英文里带 `not`）
   因此 `C2=T`，仍会被误判只读——**恰是要救的人群本身被吞掉**。
3. **判据 3 的无词表代理退化为「永远为假」。** 28 条里 `C3` 全部为 F：只读措辞几乎从不独占
   一个分句（「不要修改任何文件」「不要改代码或验收脚本」都会残留字符）。
   要真正区分「条件从句」和「具名对象」，必须有条件标记集（如果/若/万一/再/if…）
   或对象形态规则 → 第十一次加词。**不加词就写不出判据 3，这是决定性证据。**

## 4. 对方案的影响（建议）

- 方案 1a 的「措辞存在性 + 判据 2 + 判据 3」组合**不可实施**，不应进入实现。
- 与用户已定的第二条通道一致，唯一自洽的方向是：**整轮只读的来源整体移出措辞**——
  由任务类型/显式声明承载（子 agent 任务书、验收/`E2E` 声明的只读标记，
  由 `delegate_tasks` 这类调用方显式传入），普通对话里的措辞只影响**给模型的指令**。
  这条路不需要新词表（它是结构化信号），也不需要新增用户侧开关。
- 护栏 1（`先分析一下，不要改代码` 必须 `explicit_read_only`）在这条路下需要重新定位
  ——这正是用户已标注的「要改规格和护栏测试」那一条，本次保持原样。
- 若坚持「措辞仍要能触发整轮只读」，唯一不改词表可行的形态是**把措辞要求收紧到整轮独占**
  （例如：整条消息只由只读措辞与标点构成），它会让 #26/#27 这类「带具名对象的整轮只读」
  一起失效——等价于把门禁收窄到近乎不用，收益与代价需要用户明示取舍。
