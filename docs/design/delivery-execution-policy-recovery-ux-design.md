# 交付执行策略与失败恢复：UX 设计

## 用户心智

用户授权的是“把这个任务交付到指定边界”，不是逐条 shell 命令。产品应展示一条
可恢复作业流，而不是在 `gh`、权限弹窗、CI 轮询和 `deliver_changes` 之间来回跳。

## 状态表达

| 状态 | 用户文案 | 自动动作 |
| --- | --- | --- |
| `authorized` | 已获本会话交付授权 | 不重复询问 |
| `checks_registering` | 正在等待 GitHub 注册必需检查 | 稳定观察，不宣称绿色 |
| `checks_running` | 必需检查进行中（完成数/总数） | 受控轮询 |
| `merge_queued` | 已启用受规则保护的自动合并 | 等待 GitHub，不走 admin |
| `merge_reconciling` | 正在核对上次合并请求的远端结果 | 查询 PR/head/merge SHA |
| `merged` | PR 已合并（附 PR 与 commit） | 进入 release |
| `blocked` | 精确原因与可执行恢复动作 | 不伪装成权限不足 |

## 文案约束

- 动作意图拒绝：`你当前明确要求只分析，因此已跳过会产生变更的 <action>。`
- 工具权限确认：`此工具按会话模式需要确认。`
- GitHub 认证失败：只在实时认证探测失败时显示。
- CI 门禁：列出 pending/failed checks；不得写“账号没权限”。
- head 漂移：`PR head 已变化，需要对新提交重新验证。`
- 禁止出现：`改用 --admin`、`请再授权一次`（已有 standing grant 时）、
  `CI 已绿`（稳定终态前）、`稍后再让 deliver_changes 恢复`（未完成远端核对时）、
  `本回合是只读审视`（产品没有固定回合锁）。

## 边界路径

1. 用户明确说“先别合并，只分析原因”：仅暂停 merge/release 动作，仍允许完成原因
   分析；后续新意图立即重算，不形成固定回合模式。
2. 用户只问“为什么没权限”：解释真实原因并继续既有交付，不把问句当撤销。
3. PR checks 从 0 → 部分 → 完整：一直显示注册/运行中，直到稳定终态。
4. App 在 merge 请求后重启：重新打开任务时自动进入 `merge_reconciling`。
