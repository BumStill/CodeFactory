# 交付执行策略与失败恢复：业务设计

## 问题

一次已经得到用户授权的交付，在 GitHub required checks 尚未注册完成时被
`deliver_changes` 误判为 CI 绿色，随后立即合并被规则集拒绝。用户追问原因时，
当前消息又被默认归入 `ReviewOnly`，覆盖了会话已有的交付授权。模型继续尝试裸
`gh pr merge --auto`，被结构能力门禁拒绝，却错误解释成“高风险命令被拦截”，
最后承诺了一个实际会被 `intent_merge` 回执阻断的恢复路径。

这不是单点命令权限问题，而是交付授权、CI 观察、合并执行、回执恢复和事实表达
五层没有形成同一状态机。

## 目标

- 用户一次明确授权“提交、合并、发布”后，授权作为持续会话意图跨消息、跨重启
  保留；用户可随时明确暂停或撤销。具体外部重试仍由绑定 repo/branch/head 的交付
  回执约束，不能把会话授权误当成对任意仓库的无限写权限。
- 普通追问、纠错和失败原因问题不撤销既有交付授权，也不要求用户重复确认。
- GitHub required checks 未完整注册或未完成时，绝不宣称 `ci_green`。
- 合并必须走规则集允许的 auto-merge，并绑定预期 head SHA；不使用 `--admin` 绕过。
- 写前回执后的不确定结果必须先核对远端事实，再安全续接；不能永久卡死，也不能
  盲目重复外部动作。
- 用户看到的阻断原因必须区分：当前动作意图、工具权限、GitHub 认证、CI 门禁、
  合并队列和远端结果不确定。

## 非目标

- 不把裸 `gh pr merge` 变成默认产品交付接口。
- 不降低 GitHub ruleset、required checks、review、release 或 live verifier 门槛。
- 不把“管理员可绕过”当作自动恢复方案。

## 成功标准

1. 不再把一条用户消息固化为整个“回合”的互斥模式；每个工具动作都根据当前显式
   约束、持续任务授权和动作类型重新判断。
2. 已授权任务中，用户说“为什么没权限”时仍保留交付意图，除非同时明确说
   “先只分析/不要执行/取消交付”。
3. PR 刚创建且 check-runs 为零或只注册了一部分时，交付状态保持 `ci_pending`。
4. GitHub CLI 合并参数包含 `--auto --match-head-commit <sha>`，不包含 `--admin`。
5. 遗留 `intent_merge`：远端已合并则升级回执并继续；远端仍开放且 head 未变则
   安全续接；关闭未合并、head 漂移或无法核实时 fail closed。
6. 最终文案不再出现“本回合固定为只读”；只说明某个具体动作与当前显式意图冲突，
   且相同拒绝在一次执行链中只展示一次。
