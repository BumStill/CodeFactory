# 会话执行治理：业务设计

## 要解决的问题

正式版轨迹显示，用户一句话可能触发数十次工具调用；明确“只分析不修改”的回合仍发生编辑；交付工具业务上阻断却被记录为 done；完成门禁反复生成、拒绝和恢复候选回复。用户看到的是重复和失控，而不是可靠的长任务执行。

## 产品承诺

1. 用户意图决定本回合能做什么，权限设置只决定允许范围内是否需要确认。
2. Review、Implement、Deliver 是逐级能力，不互相偷跑。
3. 交付先证明整条目标链可达，再产生 commit/push 等副作用。
4. 缺验证只补一次明确证据；仍不足就如实结束为 verification incomplete。
5. 长任务仍是一条可见会话；内部按 task segment、进度快照和 attempt history 收敛。
6. 用户说“继续”或运行中纠正方向时，系统必须更新真正的执行契约，而不是只让模型读到一句话、工具层却保持旧状态。

## 用户价值与边界

- “分析一下，别改”可被当作硬承诺，不取决于模型是否听话。
- “修复”默认止于本地实现和验证；“发布/上线”才允许进入交付链。
- 发布产物与真实上线分开表达，只有 live verifier 成功才说“已上线”。
- 不删除历史审计数据；通过结构化状态减少用户正文和 UI 的重复。

## 成功指标

- Review-only 回合 mutation backend 调用数为 0。
- 每个 root turn completion recovery 不超过 1。
- “只读审视 → 用户批准 → 实施”路径不再出现第二次确认，下一次 mutation 可执行。
- capability/permission 拒绝后的状态不得显示“任务已完成”。
- `deliver_changes` 的业务 blocked 与 DB/stream/UI status 完全一致。
- 100 次同阶段进度更新在 UI 中仍是 1 个最新状态。
- 同一逻辑子任务多次重试只显示 1 张任务卡，attempt 可追溯。
- 单个工具连续运行超过 30 秒时，用户不再只看到冻结的泛化文案；活动卡至少每 30 秒刷新一次脱敏状态，60 秒后明确显示“仍在运行”及工具类别。
- 同一 root turn 达到 40 次工具调用时，只产生 1 次可见的放大风险提醒和 1 次框架收敛提示；不因为计数本身强行终止真实复杂任务。
- 统计口径明确区分整回合墙钟时间、授权等待时间与工具实际执行时间，不能把外部排队或用户审批冒充为工具运行。

## 长等待与工具放大治理

长工具调用本身不等于失败。构建、发布、外部 CI 观察和大仓库验证可能合理地运行数分钟；产品需要解决的是“用户不知道还活着”和“模型没有意识到自己已经放大”两件事，而不是设置一个会误杀真实工作的固定超时。

因此采用两级治理：

1. 单工具执行期间周期刷新同一张活动快照，只展示工具类别、已等待时间和当前阶段，不写入新的聊天气泡，也不暴露命令参数、路径或输出。
2. root turn 总工具调用数达到阈值时，向用户显示一次诊断提示，并在下一轮给模型一次收敛约束：复用已有证据、停止重复探测、说明剩余 blocker。该提示是诊断信号，不改变 Review/Implement/Deliver 能力，也不自动宣告 blocked/completed。

## 非目标

- 不让自动意图识别替代不可逆操作确认。
- 不承诺所有 forge/PaaS 都有内置 adapter；缺能力时应早阻断。
- 不把 plan/spec 变成新的常驻设置模块。
