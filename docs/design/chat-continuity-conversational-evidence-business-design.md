# 会话连续执行与自然工具证据业务设计

## 问题

CodeFactory 的用户目标是“把任务搞定”，而不是“消耗完一次模型循环预算”。当前实现把内部 `max_iterations` 同时当作资源保护和用户回合终点：当最后一轮仍产生工具调用时，系统可以只发出空 `Done`，不生成最终回复、不解释原因，也不提供恢复入口。工具修改已经发生，但聊天停在最后一条工具结果，用户无法区分模型仍在工作、任务已中断、应用卡死或结果丢失。

会话页面同时把每次成功工具调用画成有完整边框的独立卡片。长任务中，工具证据比助手叙述更醒目，连续黑框切碎对话；历史恢复后，每条持久化 assistant 行又独立占据大间距，进一步把一段自然对话变成构建日志。

## 业务决策

### 用户目标没有可见轮次上限

内部仍允许设置单个执行分段的资源预算，用于检查取消、保存进度、刷新上下文和防止单次 future 无界占用；该预算不是任务终止条件。分段预算耗尽但任务未完成时，系统必须保存连续性检查点并自动续段，不得把“达到 N 轮”显示成用户需要处理的失败。

任务只有在以下条件之一成立时才可停止：

- 已满足当前目标与验收条件，并生成最终回复；
- 遇到真实、可说明且无法由当前权限和环境自行解除的阻塞；
- 需要用户新增授权、不可逆决策或超出原任务范围的选择；
- 用户主动停止后续执行；
- 连续策略没有材料进展，系统已换过策略并能给出具体失败证据。

成本、轮次和上下文是内部调度信号，不得伪装成完成。

### 中断必须是可恢复的产品状态

模型 transport 失败、工具异常、后台 task panic、应用退出或分段续跑未成功调度，都必须落库为同一用户回合的连续性状态。前端收到事件或重启 hydration 后，应在原对话位置用一句自然语言说明发生了什么、保留了什么，以及系统是在自动恢复还是需要点击“继续执行”。

不得留下只有工具结果、没有终态语义的悬空回合；也不得仅依赖内存中的 `streaming`、`chat_cancels` 或最后一个 WebView 事件判断任务状态。

### 工具证据服从对话

助手叙述是主阅读线，工具调用是相邻的可展开证据：

- 成功的读取、搜索、编辑和命令默认是一行低对比记录，不使用完整外框；
- 运行中、等待权限、失败和中断可以使用轻背景或左侧状态线，但不能把整页变成状态卡集合；
- 连续例行成功项可折叠为一句“已完成 N 项检查”，展开后仍按原顺序可审计；
- 当前正在执行的 root turn 必须按发生顺序连续展示，不得因 segment 数量达到固定阈值而整体隐藏较早叙述和工具证据；
- 只有回合进入 completed、blocked、cancelled 或 failed 等终态后，才允许把较早执行过程收束到可展开入口；这只改变展示密度，不改写原始记录；
- 最终结果仍是普通助手回复，不切换到单独的 dashboard 或“结果模式”；
- 自适应只改变信息密度和展开程度，不在三套页面模式之间跳转。

### 项目记忆自动沉淀

聊天气泡不提供手动 `Remember` 控件。系统在会话后学习阶段基于真实对话和工具证据提取候选，只把安全、稳定、可复用的 project-scope memory 自动写入 `.codefactory/memory.md`；Profile 保留完整查看、编辑和清理能力，避免把半成品或系统状态长期固化。

## 业务成功标准

- 触发 30、80 或其他内部执行分段边界时，用户仍看到任务自动继续；不会出现空白终止。
- 应用在最后一个成功工具调用后异常退出，重启后 5 秒内显示“正在恢复”或“执行已中断，可继续”，并保留已完成修改。
- 后台 Agent task panic 后 2 秒内出现可读错误，数据库存在可追溯终态，不永久显示运行中。
- 20 个成功工具调用的会话首屏以助手对话为视觉主体，不出现 20 个深色全周边框。
- 运行中的长回合即使超过 10 个 segment，也不显示“展开较早的执行过程”；终态到达后才自动收束较早过程。
- 同一回合无论 live stream 或历史 hydration，都不显示手动 `Remember` 控件；符合准入的项目记忆由会话后学习自动写入。
- 浅色、深色、1366×768 和 800×600 的真实 App 主路径均可读、无横向溢出。

## 风险与边界

- “无用户可见上限”不等于无条件死循环。重复失败签名、无材料进展、取消和权限边界仍必须收敛，但收敛结果必须可见、可解释。
- 自动续段不能重复执行已成功的非幂等工具。检查点必须记录最后确认的模型/工具边界，并从其后继续。
- 工具摘要不得泄漏 secret、完整 prompt、大段 stdout、文件正文或未经脱敏的参数。
- 本能力不承诺应用被强制结束时继续后台运行；它承诺重启后识别并恢复或明确交接。
- 本切片不重做完整聊天信息架构，也不把 Specs、计划或任务管理固化进聊天工具栏。

## P0–P3 落地顺序

- P0（已完成，PR #235）：运行中的 root turn 禁止整体自动折叠；完成后才允许收束较早过程。
- P1 执行路线：长任务通过结构化 plan event 报告步骤状态、等待原因和计划变化；会话内显示紧凑进度条。
- P2 结果快照：终态形成结果卡和结果视图，可在最终结论与完整过程之间切换，并能只依据真实工具证据重新总结。
- P3 时间估算：结合当前任务阶段、同项目历史构建时长和外部 job 状态给出时间区间；样本不足时不展示。

验收底线：

- 运行中不再出现“展开较早的执行过程”；
- 50 分钟任务能一眼看到当前步骤、下一步、等待原因和计划变化；
- 千级事件仍满足现有有界内存门槛；
- 最终结果在终态后 5 秒内形成；
- 任何百分比和时间区间都能展示确定的数据来源。
