# 端点能力感知自动切换业务设计

> 交付分层：本次上线先解决“已配置且有凭据的端点在安全模型调用边界自动接管”、
> Keychain 卡死、自然状态展示和 subagent 固定时长中断。能力元数据筛选继续由模型
> 控制面演进；跨进程 episode 与候选耗尽后的 ownership 统一接入 CF-ORC，不再保留
> 人工技术恢复按钮作为目标设计。

## 问题

CodeFactory 当前把一次会话绑定到设置中的默认端点。模型请求遇到 `503 Service
Unavailable`、`circuit_open`、限流、网络超时或端点凭据失效时，只会在同一路由内
重试；重试耗尽后整个用户回合失败。即使本机已经配置了另一个有凭据、支持当前任务
能力且可正常调用的端点，系统也不会继续。

这不是“模型质量自动路由”问题，而是主路径可用性问题。用户选择 CodeFactory 完成
目标，端点只是完成目标的执行资源。首选服务暂时不可用时，产品应在不重复副作用、
不改变权限和不丢失上下文的前提下，使用本机已经可用的兼容端点继续。

真实故障还暴露了两个体验问题：

- `模型连接重试 1/3`、`2/3` 占据对话，但没有告诉用户接下来会怎样；
- 最终只展示 provider 原始错误，没有说明其它端点为何没有接管，也没有给出可执行的
  修复动作。

## 业务决策

### 首选端点不是单点故障

每个用户回合先使用用户当前选择的端点和模型。只有该 route 发生已分类且可安全重放的
不可用故障时，系统才从**本机已配置、有模型且凭据可读**的端点中选择下一候选。自动
切换是故障恢复，不是后台持续做质量、价格或偏好优化。

本次上线候选必须同时满足：

- 端点存在、没有被用户禁用，且本机凭据可读取或该协议不需要 API Key；
- 有可解析的 active model；
- 没有在本次故障恢复中以相同失败签名尝试过；
- 不违反用户取消、权限、隐私或成本边界。

本轮 tool calling、图片、上下文窗口和 reasoning compatibility 的静态预筛选是后续
增强。本次版本继续使用现有 context/vision/tool-choice 兼容逻辑，并在已经出现可见
输出或工具意图后禁止切换，从而避免不安全重放。

只凭模型名称、远端模型目录或内置 preset 不能证明端点可用。系统不得使用用户没有
配置的端点，也不得猜测、复制或记录明文凭据。

### 自动切换保持同一用户目标

切换发生在同一 session、root turn 和 continuity segment 内。用户目标、历史上下文、
已完成工具结果、权限决定、取消状态、成本归属与连续性检查点全部保留。不同 provider
可重新编码为各自合法协议，但不能把一次切换伪装成新用户请求。

已经成功的非幂等工具不得因换模型重放。模型应从最后持久化的 tool outcome 之后继续，
而不是重新解释并执行整个回合。

### 失败分类决定动作

- `503`、`529`、`429`、连接超时、临时 DNS/网络错误、`circuit_open`：
  对当前 route 做少量取消感知退避，然后切到下一合格 route。
- `401`、`403`、凭据缺失或凭据存储不可读：把当前 route 标记为本回合不可用，继续
  尝试其它合格 route；最终说明需要重新登录、补充 Key 或修复凭据存储。
- 模型不存在、字段或 tool-choice 不兼容、图片不支持、上下文窗口不足：优先使用当前
  provider 已有的确定性适配；仍失败时只切到满足对应能力的候选。
- 内容安全拒绝、工具权限拒绝、用户取消、不可逆操作等待确认：不是端点故障，禁止
  通过换模型绕过。

### 自动恢复必须有界

同一故障恢复 episode 维护已访问的 `(endpoint, model, failure_class)` 集合。每个候选
route 最多进入一次，候选用尽即结束当前 route approach 并进入 objective remediation。
禁止 `A → B → A`、模型别名互换或重新读取设置造成无限 ping-pong。

新的 episode 只能由 supervisor 在退避到期、健康证据变化或凭据完成事件后创建；不能
靠人工按钮或在同一回合里重置访问集合继续循环。

### 不静默降级，也不擅改用户默认值

自动切换成功时，对话中自然显示：

> ChatGPT 暂时不可用，已切换到 DeepSeek v4 Pro，继续处理。

提示至少包含原 route、目标 route 和简化原因。它是低干扰的执行状态，不是红色错误
卡片。若候选会损失本轮相关能力，系统不得静默切换；能力不足的 route 应被排除。

自动切换只改变当前回合的 effective route，不修改全局
`default_endpoint/default_model`。任务完成后可以提供“以后默认使用此端点”的明确
动作，但不得替用户自动决定。

### 候选耗尽时仍由系统持有

没有合格 route 时，objective 状态必须用自然中文说明：

- 首选端点的可读失败原因；
- 本机其它端点分别因缺凭据、缺模型、能力不匹配或本次已失败而被排除；
- 已完成工具和修改是否保留；
- recovery owner、当前 remediation、下一次安全观察；只有确认缺少不可替代凭据/额度时显示一次 core-input 动作。

原始 provider body、request id 等诊断信息放入可展开详情；首屏不能只抛原始 JSON。

## 业务成功标准

- ChatGPT 返回连续 `503 circuit_open` 时，若本机 DeepSeek 有有效凭据和兼容模型，
  系统在同一回合自动接管并完成回复。
- 切换前已经成功执行的非幂等 fake tool 在整个回合只执行一次。
- context、vision 和 tool-choice 现有确定性兼容路径不回归；可见输出后不跨模型重放。
- 两个端点均失败时，每个合格 route 最多尝试一次，随后进入 durable remediation；技术耗尽不要求用户推动。
- 用户取消、工具拒绝或内容安全拒绝后不发生 endpoint failover。
- 重新打开历史会话仍能看到脱敏的切换提示和最终回复，不显示假运行。
- 自动切换不会改变设置页中的默认端点。

## 非目标

- 不建设通用 `RoutingPolicy DSL`。
- 不基于未验证的“模型质量分”在健康 route 之间持续调度。
- 不自动购买额度、刷新订阅、创建账号或复制凭据。
- 不承诺能力不等价的模型可以无损接管。
- 不用 failover 掩盖用户取消、权限边界、内容安全策略或代码缺陷。

## 风险与边界

- 健康探测本身可能产生费用或触发限流；凭据存在和静态能力只能筛选候选，真实可用性
  由本次模型调用证明，不做高频后台 ping。
- provider 间上下文和工具协议不同；必须从规范化会话模型重新编码，不能转发原始 wire
  payload。
- 切换会改变价格、延迟和输出风格。成本继续记录到真实 endpoint/model，并在最终用量
  中可追溯。
- 端点设置可能在回合中变化；当前 failover episode 使用开始时的稳定候选快照，下一
  用户回合再读取新设置，避免运行中候选集合抖动。
