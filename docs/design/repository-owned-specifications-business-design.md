# 仓库归属规范与会话内计划：业务设计

## 业务问题

独立“规范工作台”把 CodeFactory 做成了规范内容的所有者：用户需要离开会话进入另一套
页面，规范被写进产品专属目录，任务拆分又有单独入口。结果是同一项工程意图可能同时
存在于聊天、任务树、`.codefactory/specs/` 和 `docs/specs/`，用户无法判断哪一份是真实
依据。

## 业务决策

CodeFactory 是执行与协作工具，不是规范仓库。长期业务和工程意图必须跟随代码库；计划
是一次会话的执行状态；Agent 只负责发现、读取、修改和交付这些仓库资产。

## 用户价值

- 换 Agent、换机器或从 GitHub 打开仓库时，规范仍和代码一起存在。
- 评审者在同一个 PR 中看到“为什么改”和“改了什么”，不依赖 CodeFactory 私有状态。
- 用户只需要描述任务；规划、委派和进度自然出现在会话中，不再学习第二套工作流。
- 消除 `docs/specs` 与 `.codefactory/specs` 双重权威，降低过期规范误导实现的风险。

## 产品边界

### In scope

- 移除规范/计划的一级产品入口和独立工作台。
- 会话 Agent 发现并按需读取仓库规范。
- 持久设计文档作为普通 Git 文件修改和交付。
- 保留历史任务与证据 provenance。

### Out of scope

- 不建设新的文档管理器、知识平台或规范数据库。
- 不自动迁移其他用户仓库中未跟踪、未确认的旧目录。
- 不删除历史 SQLite 字段或重写 Evidence Pack。
- 不强制所有仓库都采用 CodeFactory 自己的 frontmatter 格式。

## 成功指标

- Workspace 常驻入口中没有“规范”“计划”“拆任务”。
- 新执行路径不会创建 `.codefactory/specs`。
- 需要长期沉淀的变更在代码仓库普通文档中可见并随 PR 交付。
- 复杂任务仍可由 `delegate_tasks` 自动委派，且只在当前会话显示进度。
