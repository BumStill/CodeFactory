# Token 用量与预算业务设计

## 1. 决策

CodeFactory 将 Token 从会话底部的技术计数升级为可行动的运行仪表。产品采用三级信息架构：

```text
新会话今日摘要 -> 设置「用量与预算」深度分析 -> 高消耗会话/端到端日志定位
         \-> 当前会话底栏继续展示上下文与会话用量
```

新会话负责在任务开始前回答“今天是否还适合继续、换模型或降低推理强度”；设置页负责回答“用量发生在哪里、为什么异常、是否接近预算”。GitHub 风格的 Token 消耗地图是设置页的核心趋势视图，新会话只显示最近 28 天缩略图。

本能力不能直接复用现有 `cost_entries` 数字后上线。当前 Agent 只在无工具调用的最终轮记录成本，中间模型轮次会漏计；统一 `$1/M input + $3/M output` 也不能代表 ChatGPT 订阅、Provider 实际费用或本地模型成本。业务顺序必须是“逐请求数据真相 -> 用量视图 -> 预算与异常行动”，不能先做一个看似完整但口径错误的看板。

## 2. 行业参照与取舍

- OpenAI Usage Dashboard 提供时间范围、项目/模型分组、Usage 与 Cost 分离并明确 UTC；CodeFactory 首发采用“用量与费用语义分离”和本机时区“今天”，模型/项目筛选留作后续增强。参考：<https://help.openai.com/en/articles/10478918-api-usage-dashboard>。
- Cursor 把产品内提醒与后台分析结合，支持 50%/80%/100% 阈值和按产品入口拆分；CodeFactory 采用同样的“即时感知 + 详情下钻”，并按交互会话、自主任务、子 Agent、Evals 拆分。参考：<https://cursor.com/changelog/05-04-26>。
- OpenRouter 在模型响应中返回 prompt、completion、reasoning、cached tokens 和费用，并可按 endpoint/model/provider 聚合；CodeFactory 将逐次 Provider 响应作为计量输入，但允许字段缺失，不用估算值冒充实际值。参考：<https://openrouter.ai/docs/cookbook/administration/usage-accounting>、<https://openrouter.ai/docs/api/api-reference/analytics/get-user-activity>。

取舍：首版不做跨设备云端账单中心，不依赖外部 Usage API 才能展示，也不把 Token 多寡解释为任务质量。它首先是本机、逐请求、可追溯的运行观测能力。

## 3. 用户、任务与价值

### 3.1 目标用户

- 本地开发者：在开始任务前看清当日消耗和预算余量。
- 高自治任务使用者：发现重复、冗长或循环调用，并定位到具体作业日志。
- CodeFactory 维护者：比较不同模型、Provider、执行入口的消耗结构，验证优化是否减少无效请求。

### 3.2 核心用户任务

1. 打开新会话，立即看到本地今日 Token、请求次数、成本语义和预算状态。
2. 点击“查看详情”，进入设置的「用量与预算」。
3. 在 Token 消耗地图中识别高峰日，点击格子筛选当天明细。
4. 查看当天按执行入口和会话的拆分。
5. 从高消耗会话进入现有端到端作业流或日志，判断是正常复杂任务还是重复/循环执行。
6. 配置 Token 预算；达到阈值时收到本机提醒，但系统不擅自停止或降级任务。

### 3.3 业务价值

- 可预期：任务开始前已有预算感知，而不是月底才看到消费。
- 可解释：总量可下钻到真实模型请求、会话和作业日志。
- 可治理：Evals、子 Agent 和自主任务不再藏在普通聊天总量里。
- 可优化：能用请求数、输入/输出比、缓存命中与单会话占比识别循环和上下文膨胀。

## 4. 产品范围

### 4.1 首版纳入

- 新会话的今日用量卡和最近 28 天迷你消耗地图。
- 设置一级「用量与预算」页：今天、7 天、30 天摘要，以及 90 天、半年、一年地图。
- 最近一年 GitHub 风格 Token 消耗地图，支持 Token、预算占比、请求次数三种指标。
- 总 Token、输入、输出、请求次数；Provider 能提供时补充 reasoning、cached token。
- 实际费用、估算费用、订阅、本地、未知五类成本语义，绝不合并成一个虚假美元数字。
- 按 `interactive | autonomous | subagent | eval` 执行入口拆分，并列出高消耗会话。
- 高消耗会话及现有会话、任务、Evolution/Eval 作业日志的深链。
- 日/月 Token 预算和 50%/80%/100% 本机提醒。
- 当前会话底栏继续显示会话用量和上下文占用，并深链详情。

### 4.2 首版不纳入

- 账单支付、Provider 余额充值、自动购买或交易。
- 未经用户确认自动切换模型、停止任务或改变权限。
- 跨设备云同步、团队账单、组织配额和 RBAC。
- 依赖价格估算得出的财务报销或 Provider 对账结论。
- 用 Token 消耗直接推断任务成功率、回答质量或员工绩效。
- anonymous 会话持久化；匿名只显示本次内存态用量并明确“不计入今日”。
- 模型、Endpoint、项目多维筛选、自定义起止日期和跨设备团队账单；这些属于后续分析增强，不阻断本次每日统计首发。

## 5. 指标合同

### 5.1 主指标

| 指标 | 定义 | 展示规则 |
| --- | --- | --- |
| 每日总 Token | 当地日界内每个已计量模型请求的 `input_tokens + output_tokens` 之和 | reasoning/cache 若是 input/output 子集，不重复相加 |
| 模型请求数 | 真实完成或返回 Usage 的 Provider 请求数 | 不等于用户消息数、工具调用数或 SSE chunk 数 |
| 实际费用 | Provider 对该请求明确返回的实际费用之和 | 缺失时保持空值，不用默认价格补齐 |
| 估算费用 | 按已知模型价格对请求进行的显式估算 | 与实际费用分栏并标记“估算” |
| 预算占比 | 当地日或月累计 Token / 用户配置 Token 预算 | 未配置预算时不显示进度百分比 |

### 5.2 诊断指标

- 输入、输出、reasoning、cached token；缓存命中率按 Provider 可用字段计算。
- 按执行入口和会话的 Token 与请求次数。
- Top 会话占当日用量比例，用于发现单任务失控。
- 最近 7 日均值及相对变化；数据不足 7 个完整当地日时明确标注样本天数。

### 5.3 数据质量护栏

- 带 Usage 的模型响应应全部进入计量；首发通过来源计数、缺失计数与汇总对账暴露覆盖情况，跨版本 99.9% SLO 留待后续遥测基线建立后启用。
- 同一逻辑请求因 UI 重放、恢复或事件重送不得重复计数；真实 Provider 重试是新的付费用量，应按独立 attempt 记录。
- 新记录到可见 UI 的本机刷新目标不超过 2 秒。
- `无数据/采集缺失` 与 `已采集且为 0` 必须是不同状态。
- 各执行入口、模型或会话拆分在同一过滤条件下必须与总量一致。
- Token 成本、任务质量、Eval 结论和完成状态分别呈现，不能互相替代。

## 6. 成本语义

每条用量记录必须有 `cost_source`：

- `provider_actual`：Provider 返回真实成本，显示“实际费用”。
- `model_price_estimate`：CodeFactory 按版本化模型价格估算，显示“估算费用”。
- `subscription`：如 ChatGPT OAuth 订阅，只显示 Token 和“订阅流量”，不伪造增量美元成本。
- `local`：本地模型显示“本地”，可显示 `$0` 但不暗示硬件成本为零。
- `unknown`：只显示 Token；费用位置显示“不可用”。

同一汇总范围内存在多种成本语义时，UI 分项展示，不把订阅、本地和估算折算进“实际费用”。

## 7. 成功、风险与停止条件

### 7.1 首版成功标准

- 工具密集型任务的每一轮模型请求都进入统计，汇总与逐请求 fixture 精确一致。
- 用户能从新会话在两步内到达某个高消耗日的具体会话或作业日志。
- ChatGPT 订阅不显示虚假按量费用；Provider 实际费用与估算费用不混淆。
- 地图能区分高峰、超预算、零用量与缺失数据，并可通过键盘完成日期选择。
- 1366×768 与 390×812 均可完成主路径，无关键数据、筛选或动作被遮挡。
- PR+CI、迁移证据、真实 Dev App、锁屏可运行 headless 门禁和发布安装包验证全部完成。

### 7.2 直接拒绝验收

- 仍只记录最终回复，或把会话消息数冒充模型请求数。
- 用统一默认单价把订阅/未知成本显示为实际美元。
- 日界固定按 UTC，却在界面写“今日”而不说明。
- 地图用颜色表达全部语义，键盘用户无法获得精确值。
- UI 已出现但数据只能由 mock、空表或迁移后的重复记录支撑。
- Dev、PR 或 CI 通过后即宣称 `live`，没有刻意发版和精确发布产物证据。

## 8. 分阶段交付

1. **Phase 0 — Usage Truth**：逐 Provider 请求采集、幂等、成本语义、当地日界和兼容迁移。
2. **Phase 1 — Daily Surfaces**：新会话今日摘要、当前会话底栏修正、设置基础统计和实时刷新。
3. **Phase 2 — Usage Map & Drill-down**：年度消耗地图、28 天缩略图、筛选、高消耗会话和日志深链。
4. **Phase 3 — Budget & Alerts**：日/月 Token 预算、50/80/100% 本机提醒和异常标记。
5. **Phase 4 — Release Proof**：跨 Provider/平台兼容、真实 App、headless、PR+CI、安装包及公开产物复验。

完成 Phase 0 至 Phase 3 但未完成 Phase 4 时必须标记 `not live`。
